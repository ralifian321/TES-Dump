NATIVE RVA HOOK MONITOR — BLUEPRINT PEMBUATAN APK
===============================================

TUJUAN
------
Membuat APK modul LSPosed baru yang tidak mempunyai fitur gameplay Ala Mobile.
APK hanya berfungsi sebagai native runtime hook/monitor untuk target game IL2CPP.
Target game dapat diganti melalui LSPosed Scope. APK game TIDAK direpack, TIDAK
rebuild, dan libil2cpp.so game tetap berada di APK/proses game asli.

FITUR YANG DITARGETKAN
----------------------
1. Masuk ke proses target melalui LSPosed/LibXposed.
2. Menunggu dan mendeteksi libil2cpp.so di proses target.
3. Membaca base address libil2cpp.so secara runtime.
4. Resolve address = base + RVA.
5. Monitor pemanggilan method pada RVA tertentu.
6. Native inline hook dengan ShadowHook.
7. ARM64 instruction intercept dengan ShadowHook.
8. Membaca register ARM64 pada callback intercept.
9. Mengubah parameter/return value melalui proxy/intercept bila signature sudah diketahui.
10. Runtime patch byte terpisah dari ShadowHook, dengan backup + restore.
11. Registry hook aktif: RVA, absolute address, mode, status, stub, original pointer.
12. Tombol Enable/Disable/Restore per hook.
13. Log runtime: base, RVA, absolute address, install/uninstall, invocation count,
    register/argument snapshot yang dipilih, dan error ShadowHook.
14. Target package custom/universal dari sisi konfigurasi LSPosed; kode native tidak
    digabung dengan satu game tertentu.
15. Arm64-v8a sebagai ABI utama.

BATASAN PENTING
---------------
- ShadowHook adalah inline hook engine, bukan injector/profiler IL2CPP universal.
- ShadowHook tidak mengetahui class/method IL2CPP. Nama method/RVA berasal dari metadata,
  dump, analisis ELF, atau konfigurasi pengguna.
- ShadowHook melakukan function hook/intercept. Direct arbitrary byte patch bukan
  fungsi utama ShadowHook; untuk itu dibuat PatchEngine terpisah.
- ShadowHook sendiri dapat menyediakan original-function/trampoline pointer setelah hook.
  Trampoline custom yang sepenuhnya dikelola aplikasi adalah komponen berbeda dan tidak
  perlu untuk versi pertama.
- Memantau "semua method yang dipanggil" bukan fitur otomatis ShadowHook. Versi pertama
  memonitor RVA/method yang dipilih.

FUNGSI HOOK
-----------
Hook menargetkan fungsi penuh.
Caller memberikan proxy function dengan ABI/signature yang kompatibel dengan fungsi asli.
Jika ingin meneruskan eksekusi ke fungsi asli, gunakan pointer original yang dikembalikan
ShadowHook atau mekanisme macro yang sesuai mode hook.

ORIGINAL / TRAMPOLINE
---------------------
Dokumentasi ShadowHook menjelaskan bahwa pada hook yang sukses, original address yang
tersedia untuk caller menunjuk ke jalur trampoline/original-function chain yang diperlukan
untuk memanggil implementasi asli tanpa memicu rekursi terhadap alamat function yang sudah
ter-hook.

Ini berarti kita TIDAK perlu menulis mesin trampoline ARM64 sendiri untuk function hook
versi pertama.

MODE
----
Source menyediakan konsep:
- shared
- multi
- unique

Ala Mobile menggunakan:
ShadowHook.ConfigBuilder().setMode(ShadowHook.Mode.UNIQUE).build()

Untuk module baru:
- UNIQUE cocok untuk satu controller hook yang ingin memiliki target sendiri dan mudah
  dikelola on/off.
- MULTI berguna jika target memang perlu beberapa proxy.
- SHARED dipakai bila chain antar hook dibutuhkan dan proxy mengikuti aturan stack cleanup
  ShadowHook.

REKOMENDASI VERSI PERTAMA: UNIQUE.

INTERCEPT
---------
ShadowHook juga menyediakan instruction intercept.
Callback menerima context CPU ARM64 sehingga register dapat dibaca/diubah.
Ini digunakan bila target yang dipantau adalah instruction address, bukan hanya entry
function.

UNHOOK
------
shadowhook_unhook(stub)

Stub yang dikembalikan saat install harus disimpan di registry agar tombol Disable/Restore
bisa memanggil unhook dengan benar.

AUTO-PENDING BY LIBRARY+SYMBOL
------------------------------
Manual menjelaskan bahwa hook berdasarkan library name + symbol dapat dicatat sebagai
pending jika ELF belum loaded, lalu diselesaikan ketika ELF masuk.

Untuk target IL2CPP berbasis RVA, kita tetap memakai pola:
wait for libil2cpp.so -> get base -> base + RVA -> hook/intercept.

SOURCE APP DEMO
---------------
APK demo source memiliki app/ dengan UI test. Ini hanya test harness untuk membuktikan
ShadowHook, bukan UI untuk memilih game/RVA.

E. ALUR RUNTIME END-TO-END
============================================================

1. Install NativeRvaHook.apk.
2. Aktifkan module di LSPosed.
3. Centang satu target game pada Scope.
4. Restart game.
5. LibXposed memanggil HookModule dalam proses game.
6. HookModule/NativeBridge memuat libhookcore.so.
7. libhookcore.so menginisialisasi ShadowHook.
8. Resolver menunggu libil2cpp.so.
9. Resolver mengambil base address libil2cpp.so.
10. Config target memberikan RVA.
11. Address dihitung:
       absolute = base + RVA
12. Engine memvalidasi area target.
13. User memilih:
       MONITOR
       FUNCTION HOOK
       ARM64 INTERCEPT
       PATCH
14. Engine memasang operasi.
15. Registry menyimpan stub/original/backup.
16. Event masuk ke log buffer.
17. UI menampilkan ACTIVE.
18. Disable -> unhook / restore.
19. Restart game -> keadaan proses kembali bersih jika tidak ada persistent patch di file.

============================================================
H. FUNCTION HOOK ENGINE
============================================================

Input:
- target absolute address
- proxy function
- mode UNIQUE/MULTI/SHARED
- optional original pointer

Flow:
base + RVA
   -> shadowhook_hook_sym_addr(...)
   -> stub
   -> original pointer

Registry entry minimal:
struct HookEntry {
    uint64_t id;
    uint64_t rva;
    uintptr_t address;
    void *stub;
    void *orig;
    uint32_t mode;
    uint32_t state;
    uint64_t call_count;
};

STATE:
0 = NONE
1 = INSTALLING
2 = ACTIVE
3 = DISABLED
4 = FAILED
5 = RESTORED

ON/OFF:
- ON -> install hook.
- OFF -> shadowhook_unhook(stub).
- Restore -> clear state, free associated resources, restore patch bytes jika mode PATCH.

JANGAN memanggil function asli melalui nama function yang sudah di-hook.
Gunakan original/trampoline pointer sesuai kontrak ShadowHook.

============================================================
I. ARM64 INSTRUCTION INTERCEPT
============================================================

Gunakan saat yang dibutuhkan adalah register/instruction-level observation.

API source:

Callback mendapatkan CPU context.
Tool dapat menampilkan register yang dipilih:
- x0-x7 untuk argumen umum AAPCS64
- x8-x18 bila diperlukan
- x19-x28 callee-saved/context khusus
- SP/PC/LR bila API context yang digunakan mengeksposnya

UI:
[ARM64 INTERCEPT]
RVA: 0x........
[INSTALL]

LOG:
PC=0x........
X0=0x........
X1=0x........
...

CHOOSE-ONLY LOGGING:
Versi awal sebaiknya read-only.
Jangan menulis register sampai target method/register telah divalidasi.

============================================================
J. UBAH RETURN VALUE / PARAMETER
============================================================

UNTUK FUNCTION HOOK:
Proxy function dapat:
- membaca parameter
- mengubah parameter
- memanggil original
- mengganti return value
- tidak memanggil original

SYARAT UTAMA:
Proxy harus kompatibel dengan ABI/signature target.
Source ShadowHook menekankan bahwa receiving/passing parameter harus kompatibel di
level CPU.

UNTUK INTERCEPT:
Context register dapat dibaca/diubah pada instruction point yang ditargetkan.
Ini cocok untuk kasus ketika pengguna ingin mengubah nilai register ARM64 tanpa membuat
proxy function penuh.

============================================================
K. PATCH ENGINE TERPISAH
============================================================

ShadowHook bukan generic byte patcher. Karena user membutuhkan opsi "ubah nilai di RVA",
project baru sebaiknya memiliki PatchEngine terpisah.

PatchEngine bertugas:
1. Resolve address.
2. Read original bytes.
3. Simpan backup per hook ID.
4. Ubah memory permission halaman bila diperlukan.
5. Tulis patch bytes.
6. Flush instruction cache.
7. Mark ACTIVE.
8. Restore original bytes ketika OFF/RESTORE.

DATA:
PatchEntry {
    rva;
    address;
    original_bytes[];
    patch_bytes[];
    length;
    state;
}

REKOMENDASI:
- Backup bytes WAJIB.
- Restore hanya dari backup yang dibuat dari proses yang sama.
- Validasi panjang instruksi ARM64 = kelipatan 4 byte.
- Jangan menganggap semua RVA adalah entry function.

============================================================
L. TRAMPOLINE VS ALLOCATED CODE
============================================================

1. SHADOWHOOK TRAMPOLINE
------------------------
Ini jalur yang direkomendasikan untuk Function Hook.
ShadowHook mengelola redirect/original call chain untuk hook.
Aplikasi menyimpan `orig`/stub yang dikembalikan ShadowHook.

2. CUSTOM ALLOCATED TRAMPOLINE
------------------------------
Ini fitur terpisah dan tidak dibutuhkan versi pertama.
Jika suatu saat dibutuhkan:
- allocate executable/readable memory
- emit ARM64 branch/relocation stub
- handle branch range
- flush icache
- lifetime management
- restore original bytes

Ini lebih kompleks dan lebih raw dibanding memakai trampoline ShadowHook.
Versi awal sebaiknya TIDAK mengimplementasikan custom code cave bila ShadowHook sudah
memenuhi kebutuhan.

============================================================
AD. APA YANG TIDAK BOLEH DISAMAKAN
============================================================

LSPosed != ShadowHook
- LSPosed memasukkan module ke proses target berdasarkan Scope.

ShadowHook != IL2CppDumper
- ShadowHook melakukan runtime hook/intercept.
- Il2CppDumper menganalisis binary + metadata secara offline.

libhookcore.so != libshadowhook.so
- libhookcore = controller logic milik project kita.
- libshadowhook = engine hook dari ByteDance.

PATCH != HOOK
- Patch mengubah instruction bytes.
- Hook mengarahkan function execution ke proxy.

INTERCEPT != HOOK PROXY
- Intercept bekerja pada instruction/context.
- Hook bekerja pada function entry/proxy.
